## 第二轮对话（2026-09-01）：核心构想 —— 幕布直接接入各 CLI 原始输出

### 用户原话要点

> "各个 CLI 在终端的表现都不一样。如果还是按照 codemoss / mossx 的对接方式会比较累也比较重……我的想法是幕布直接接入各个 CLI 终端的原始输出样子。"

### 要保留的能力（复刻自 codemoss/mossx，其余全砍）

1. **客户端外观** —— UI 外壳视觉复用
2. **工作区** —— 多工作区管理
3. **文件夹管理** —— 文件树（读目录、展开、打开）
4. **Git 管理** —— status / diff / commit（轻量实现，直接调 `git` CLI）
5. **对话框能力** —— composer 输入、@文件引用、发送到当前 CLI 会话

### 核心问题：原始终端接入能不能做到？

**结论：能，且是最轻的路线。**

| 维度 | codemoss/mossx 路线（结构化对接） | tmd-cli 路线（原始终端） |
|---|---|---|
| 接入方式 | 每个 CLI 写 engine adapter，解析 JSON stream | PTY spawn CLI 进程，透传字节流 |
| 渲染 | 自建会话 UI（markdown/diff/checkpoint 面板） | xterm.js 1:1 还原 CLI 原生 TUI |
| 接新 CLI 成本 | 高（适配层 + 能力矩阵 + 测试） | 低（配一行启动命令） |
| 结构化事件 | 有（token、diff、checkpoint、权限审批） | 无（默认），可旁路解析增强 |
| 维护负担 | 跟随各 CLI 协议演进，持续适配 | CLI 自管 TUI，上游升级零成本 |

**技术方案**：Rust 后端 `portable-pty` 起伪终端 → spawn `claude` / `codex` / `gemini` / `kimi` 等 → 前端 xterm.js 渲染原始字节流（ANSI/光标控制全保留）。VS Code 终端、Warp 同款方案。

**已知代价**：拿不到结构化事件（diff 视图、token 统计、checkpoint、审批弹窗）。架构上预留**旁路解析层**（从 PTY 流抽取信息），终端为主、增强为辅，MVP 不做。

### 已定方向

- 当前目录 `tmd-cli` 即为新项目根，不另建目录
- 技术栈沿用 Tauri 2 + React + xterm.js（与两项目同源，复用经验）
- 依赖目标：砍到 ~15 个以内（对比 codemoss 70+）

### 待决策

- [x] 项目正式名称 → **tmd-cli**，直译即可，不再纠结
- [x] CLI profile 第一版 → **omp cli / pi cli / codex cli** 三个
- [ ] 旁路解析层是否进入 v1 范围（用户未表态，默认搁置）
- [x] 对话框发送方式 → **必须做完善，是核心诉求**

## 第三轮对话（2026-09-01）：对话框 = 核心诉求，能力对标 mossx

### 用户原话要点

> "对话框发送方式要做完善，这个是我的核心诉求。就是因为终端 CLI 对话框太简单，我才会有这个想法。对话框能力完全参考 mossx 里的对话框能力做。"

### 关键认知修正

**对话框不是附属品，是这个项目存在的理由。** 终端原生 CLI 的输入框太简陋（单行、无 @引用、无图片粘贴、无模式切换），tmd-cli 要用一个富 composer 补齐，而输出侧仍然交给 CLI 原生 TUI 渲染。

由此确立产品的核心交互模型：

```
┌─────────────────────────────────────────┐
│  幕布（xterm.js 渲染 CLI 原生 TUI 输出）   │  ← 输出：原始终端透传
├─────────────────────────────────────────┤
│  富 Composer（对标 mossx 对话框全部能力）   │  ← 输入：结构化组装 → 写入 PTY stdin
└─────────────────────────────────────────┘
```

**架构含义**：composer 组装的最终产物（文本 + @展开的文件引用 + 图片路径等）必须能**可靠地注入 PTY stdin**。注入时机是关键技术风险——CLI TUI 处于不同状态（空闲/生成中/审批弹窗）时，stdin 写入的行为不同，需要状态探测或排队机制。此项列入技术风险清单。

### 行动

- 已启动对 mossx composer 能力的完整盘点（产出 `docs/research/mossx-composer-capabilities.md`），作为对话框复刻的需求基线。

## 第三轮补充（2026-09-01）：架构基调 —— 模块化 + 插件化，随时可插拔

### 用户原话要点

> "参考 mossx 插件分支。新的架构需要以模块化和插件化为主，随时能插拔。"

### 设计张力（必须直面）

mossx 插件分支的教训：**47 个 `packages/plugin-*` 包，拆分过细**，正是"太重"的来源之一。用户要的是插件化的**架构风格**，不是 47 个包的**物理形态**。

**取舍原则**：

| 维度 | mossx 插件分支 | tmd-cli 目标 |
|---|---|---|
| 插件粒度 | 极细（每能力一包，47 个） | 粗粒度（每个领域一个插件） |
| 插件载体 | npm workspace 包 | 单仓库 feature module + manifest 注册，成熟后再物理拆分 |
| 插件契约 | plugin-contract 包 | 轻量 Plugin interface（activate/deactivate/contributes） |
| 插拔方式 | 编译期静态链接 | 编译期注册 + 运行期开关（enable/disable） |

**第一版插件边界（草案）**：

1. `plugin-cli-omp` / `plugin-cli-pi` / `plugin-cli-codex` —— 每个 CLI 一个插件（profile、启动命令、环境变量、stdin 注入策略）
2. `plugin-workspace` —— 工作区管理
3. `plugin-files` —— 文件夹/文件树
4. `plugin-git` —— git 管理
5. `plugin-composer` —— 对话框（核心插件）

内核只负责：窗口外壳、PTY 管理、插件注册表、IPC 总线。

## 第四轮对话（2026-09-01）：架构对齐 —— 布局定型 + Composer 触发器体系

### 用户原话要点

> "插件化，模块化。对话框输入可以发送截图、拖拽文件，能接入具体 CLI 支持的命令，比如 `@` `$` `/` 这些能力。幕布完全使用 CLI 终端自己的输出内容，不额外渲染。左侧工作区会话管理，右侧文件系统。"

### 布局定型（三栏）

```
┌──────────┬─────────────────────────────┬──────────┐
│ 左侧栏    │                             │ 右侧栏    │
│ 工作区    │      幕布（xterm.js）        │ 文件系统  │
│ 会话列表  │   CLI 原生输出，零额外渲染    │ 文件树    │
│          │                             │ (git 状态) │
│          ├─────────────────────────────┤          │
│          │   富 Composer（核心）         │          │
└──────────┴─────────────────────────────┴──────────┘
```

- **左**：工作区切换 + 会话（每个会话 = 一个 PTY + 一个 CLI 实例）
- **中**：幕布 + Composer
- **右**：文件树（@引用、拖拽的数据源）+ git 状态

### 架构原则确认

1. **幕布零渲染原则（硬约束）**：输出侧 = xterm.js 透传 PTY 字节流，**不做任何消息气泡/markdown/diff 自定义渲染**。所有"增强"只允许出现在幕布之外的区域（composer、侧栏）。
2. **Composer 触发器体系**：`@`（文件）、`/`（斜杠命令）、`$`（CLI 特定命令/变量）等触发符**由 CLI profile 声明**——每个 CLI 插件声明自己支持哪些触发符及补全行为，composer 内核只做通用下拉框架，具体数据源由插件注入。**插件化的第一个落地场景。**
3. **截图/拖拽**：截图 = 系统截图 → 落盘会话临时目录 → 注入路径文本；拖拽文件 = 落到 composer 变附件 / 落到幕布变路径插入。

## 第五轮对话（2026-09-01）：外观定型 —— 完整复刻 mossx 外壳 + 头/底工具栏

### 用户原话要点

> "主客户端外观头部底部工具栏也要保留，为后续扩展做准备。另外第一版的外观样式完全复刻 mossx 的客户端外观。"

### 决策

1. **头部工具栏保留**：窗口顶栏（工作区切换、设置入口、扩展位）——为后续插件扩展预留挂载点。
2. **底部工具栏保留**：状态栏（git 分支、会话状态、扩展位）。
3. **v1 外观 = 完整复刻 mossx 客户端外壳**：不重设计，直接迁移 mossx 的布局骨架与样式体系（design tokens 直接从 mossx CSS 提取，无需另找 tokens 文件）。

### 布局更新（在第四轮三栏基础上加头/底）

```
┌───────────────────────────────────────────────────┐
│ 头部工具栏（工作区切换 / 设置 / 插件扩展位）          │
├──────────┬─────────────────────────────┬──────────┤
│ 左侧栏    │                             │ 右侧栏    │
│ 工作区    │      幕布（xterm.js）        │ 文件树    │
│ 会话列表  │   CLI 原生输出，零额外渲染    │ git 状态  │
│          │                             │          │
│          ├─────────────────────────────┤          │
│          │   富 Composer（核心）         │          │
├──────────┴─────────────────────────────┴──────────┤
│ 底部状态栏（git 分支 / 会话状态 / 插件扩展位）        │
└───────────────────────────────────────────────────┘
```

### 架构含义

- 外壳（头部/底部/三栏骨架）是**内核的一部分**，不是插件——但头/底工具栏暴露**插件挂载点**（contribution point），插件可注册按钮/指示器。这就是"为后续扩展做准备"的落地方式。
- 复刻范围限定在**外壳视觉**；mossx 外壳里的重功能（引擎切换器、配额指示等）不随迁，只留空挂载点。

## 第六轮对话（2026-09-01）：三项悬念拍板 —— git 复刻 / 会话模型 / 触发符语义

### 用户决策（原话归纳）

1. **git 管理**：完全复刻 mossx 的 git 能力。
2. **会话模型**：会话是**主入口**，与 CLI **一一对应**，适配各 CLI 自身的会话管理结构（如 claude 的 resume、codex 的会话文件）。固定绑定，不中途切换。
3. **触发符语义**：
   - `$` = 拉起 **skill**
   - `/` = **通用命令**（common）
   - `@` = **文件夹和文件**引用
   - **全部调用 CLI 自身的能力**，composer 只做入口和补全；**当前 CLI 不支持该触发符就不反应**（优雅降级，不报错、不兜底）。

### 架构含义

1. **会话-CLI-PTY 三位一体**：`Session = 1 CLI profile + 1 PTY + CLI 自身 session id`。会话列表就是左栏主入口；恢复会话 = 按 CLI 各自的方式恢复（profile 里配 resume 命令模板）。
2. **触发器体系简化**：composer 不需要实现触发符的**语义**，只需要：
   - 补全 UI（`@` 的候选来自本地文件树；`/` 和 `$` 的候选来自 CLI 插件声明的目录清单）
   - 原样透传文本到 stdin，语义由 CLI 自己解析
   - 按 profile 的 `triggers` 声明决定哪些触发符激活补全，未声明 = 不反应
3. **git 插件需求基线** = mossx `src/features/git` 的能力集（需另做一轮盘点，同 composer 的方式）。

## 第七轮对话（2026-09-01）：基础功能优化

### 用户反馈

- 独立对话当前仍是终端输入形态；富 Composer 尚未接入，符合当前开发阶段。
- 会话列表可以创建会话，但已有会话切换后无法正常恢复显示。
- 会话运行期间缺少呼吸灯提示。
- 右侧文件夹可以展开，但点击文件无法预览渲染。
- 需要增加左右工具条，并允许从底部左右角折叠对应侧区域。

### 已实施修复

1. 内核为每个 Session 常驻 PTY 输出环形缓冲，TerminalView 切换回来时先回放再接实时流。
2. 内核记录最近输出时间，SessionList 以 2 秒活动窗口显示呼吸灯。
3. files 插件增加 `fs_read_file` IPC 和文本预览 overlay（512KB 上限，二进制/非 UTF-8 拒绝）。
4. 外壳增加 `leftRail` / `rightRail` / `overlay` 插件挂载点。
5. 底部左右角提供侧区折叠按钮，状态写入 localStorage。
