任务闭环编排 · 设计形态示例(深度版)

定位一句话:引擎做拆解与执行(agent loop 自主规划),客户端做任务单、闸门与裁决。编排层是薄的一层:任务单 + 派发 + 状态回填 + 验收 gate,全部发生在幕布之外;幕布内保持 PTY 原样透传。本页是 spec 级原型:机制(时序/模板/协议/幂等)、交互(决策矩阵/通知路由/键盘)、UI(六视图 + 手机远程)三层都给到可评审颗粒度。配色与结构基准取自 1421 dev 真实客户端 token。

架构落点(全部既有纪律内)

· 新 feature 插件 task-orchestrator:attempt 状态机纯函数 + 台账读写 + 订阅面,经 activate(ctx) 注册

· 事件源零新增:RPC 轮界、activityWatch、askWatch、evidence 帧、sessionUsage,全部已存在

· 派发 = composer 既有通道注入 prompt 模板,不碰 PTY 透传铁律

· 台账写入:json 直写(既有原子写),不走 fsRenameEntry 撞名路径

· 内核零知识:编排语义全在插件侧,kernel 不出现 taskId 分支

· 手机树消费:任务徽标/审批卡走「适配器/纯函数模块」白名单,不 import 插件 UI

归档与膨胀治理

· done 任务 30 天后压缩:updates 截尾至 10 条,evidence 保留元数据(diff 统计),diff 全文进 checkpoint

· attempts[] 上限 5,竞速落选 attempt 只留统计行

协议设计要点

· 围栏名用 tmd-plan 而非通用 json:幕布渲染器不认识它,不会误渲染;编排层从 prompt_result 文本提取,幕布无感

· 解析失败零阻塞:计划卡降级显示原文,人照样能批(gate 1 永远可人工兜底)

· 变量白名单注入:title/criteria 过转义(剥 ``` 与控制符),引擎名/cwd 来自宿主枚举不来自用户输入

· 判据即契约:模板把「验收标准」前置给引擎,模型自己会往判据上收敛——这是「环境裁决」的 prompt 侧表达

二期:MCP 反向通道(引擎主动拉任务)

task_next()      → {id,title,criteria,cwd} | null
task_report(id, {step, note, evidence[]})
attempt_attach(id) → {sessionId, 已绑定?}

仅本地 loopback;工具面走插件声明的 MCP server;先用派发模板单向驱动,反向通道等用户真有「引擎空闲拉活」诉求再上。

1.7 并行策略、锁与接力协议 二期

并行:attempt × worktree

· 竞速形态:同任务开 2 个 attempt(如 omp + claude),各占 wt/<taskId>-a<n> worktree,互不污染工作区

· 无 worktree 约束:同 cwd 强制串行队列(队列位见列表视图顶栏),或派发时强制勾 worktree

· 竞速裁决:双 attempt 均 verified → 对比视图选优(成本/时长/判据);落选 attempt 记 rejected,worktree 丢弃

接力协议(额度撞墙/崩溃续命)

注入四件:

① 目标 + 判据进度(已过 c1 / 未过 c2,c3)

② 前 attempt 转录尾部摘要 ≤2k tokens——由该引擎适配器从 session JSONL 尾部 N 轮抽取,不猜私有格式

③ evidence 文件清单(+增删统计)

④ checkpoint 基线名(回滚锚点不变)

成本核算(任务维度)

· attempt.usage = sessionUsage 行聚合(cli-shared 既有 omp/pi/claude/codex 用量契约),编排层零新增解析

· 列表/详情/对比三处呈现 tokens 与时长;预算条 = 判据复杂度启发,超条不改行为只提示

· done 汇总:任务总成本写入 updates 收口行,月度视图三期再议

2.1 用户旅程六步

自动01
交代

composer 里照常说话,或任务面板「新建任务」。判据可写可补,不强制结构化。

自动02
落卡派发

选引擎与 cwd,prompt 模板注入「先出计划 + 完成判据」。开的是普通会话,幕布照常可用。

GATE 103
批准计划

tmd-plan 卡片,人批或改判据。可关(信任模式直跑),默认开。

自动04
挂机

状态回填自动推进;只有 waiting 沿打扰用户(通知三通道,失焦才发)。

自动05
应答

审批收件箱一键放行/拒绝,手机同权。应答写回会话,轮继续。

GATE 206
验收闭环

任务维度聚合:diff 预览 + 判据核验记录 + usage。人点通过,写回 done。

§6开放问题与风险(查漏补缺,诚实清单)

#问题当前立场
1settled 后续说:用户回原会话接着说,attempt 已 settled/任务已 review回退 running + 关验收视图(状态机已含);updates 记 reopen。替代方案「续说算新 attempt」拒绝:会话连续性是事实,不该被台账口径切碎
2幂等:settled/ask 事件双发、webview 重载重放幂等键 (sessionId, turnSeq),状态机纯函数侧去重;readopt 回灌走 watches.seedIdentity 既有通道,不重复登记
3prompt 注入面:任务标题/判据是用户自由文本,进模板后可能携带指令变量转义(剥围栏与控制符)+ 模板常量只注入白名单字段;残余风险接受(用户本机、自己的引擎、自己的仓库,威胁模型=防误非防恶)
4台账膨胀:attempts/updates/evidence 单调增长归档策略(30 天压缩)进一期 settings;index.json 分项目文件已天然分片
5多引擎判据方言:runCmd 对非本仓任务不通用(如文档任务没有 check:gate)runCmd 是 per-task 字段,非全局约定;无 runCmd 的 auto 判据在派发时降级为人工
6并发与锁:同 cwd 双 attempt 相互踩工作区一期直接禁(串行队列);二期 worktree 解锁;既有并行 AI 协作守则(别人在改的不碰)在编排层同样成立
7取消语义:cancelled 后会话怎么办会话不杀,降级普通会话(幕布/时间线保留,人可继续用);attempt 记 rejected。杀会话留给用户手动(幕布既有停止按钮)
8编排层会不会长成第二个「重编排产品」警戒线:任何一期/二期件必须复用一个既有底座件(RPC/watch/ask/evidence/usage/手机),否则不进本期——竞品寿命数据(task-master 放缓、vibe-kanban sunsetting)说明重编排是死路
