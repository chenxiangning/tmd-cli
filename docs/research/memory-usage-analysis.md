# 客户端内存占用分析与优化预案

- 状态:已落地(`165b4d4`/`966271a`/`848ee7b`)—— 正式 spec [2026-09-09-disk-first-session-open-design.md](../superpowers/specs/2026-09-09-disk-first-session-open-design.md);本文件保留作动机/实测/复盘底稿

## 结论

v0.1.3 内存增大不是泄漏,是「看会话 = 必须有活进程」这条架构耦合逼出来的常驻预付:为了点击秒开,启动时后台预开最多 16 个真实 CLI 进程(实测 4.9GB),再叠加 tab 保活(多个 xterm 常驻)。监控工具显示的 11.86GB 是整棵进程树合计(含 CLI 子进程);Rust 主进程有界,WebContent 经 `leaks` 实测仅 1.7KB 微漏,非经典泄漏。

**优化主线(已收敛):磁盘日志先行回放 + 进程惰性后台拉起(走法 1)**。点击磁盘会话立即用已有 `sessionHistoryPage` 原语从磁盘日志回放填充画面(百毫秒级,零进程),resume 进程后台异步起、就绪后实时流接管。秒开不再依赖任何预付,自动激活失去存在理由。

**走法 2(codemoss 同款 transcript 结构化视图)已否决**:它要求每个 CLI 写一份结构化解析适配器——正是当年弃坑 codemoss、改走 PTY 终端模拟的原因;PTY 幕布通吃一切 CLI、零适配,是 tmd-cli 的立身之本,不动。

## 实测数据(2026-09-09 17:51,release 0.1.3,已运行 3h13m)

| 组件 | 物理占用 | 说明 |
|---|---|---|
| Rust 主进程 | 214MB | 泵有界:8ms 聚合窗 + 1MB/批上限;会话日志 64MB 落盘旋转 |
| WebContent | 1.4GB(峰值 2.4GB) | 成分:WebKit Malloc ~900MB resident(88.2 万笔分配,11% 碎片),JS Gigacage 仅 224MB(大部换出) |
| WebKit GPU/辅助 | ~150MB | WebGL 上下文与栅格 |
| CLI 子进程 ×19 | **4.9GB** | 18 个 `bun omp`(97–403MB/个)+ 1 个 grok;其中 8 个在启动同一秒被 `--resume` 拉起 = 自动激活批次 |
| **整树合计** | **≈6.7GB** | omp 进程随对话上下文继续长大,跑到 11.86GB 只是时间问题 |

对照:v0.1.2 同场景(会话仅点击时拉起、单幕布挂载)启动稳态约 0.6–0.8GB 整树。

## codemoss 对照(为什么它的秒开不花内存,以及我们为什么不抄)

codemoss(`/Users/chenxiangning/code/AI/github/codemoss`,ccgui 0.9.5)的会话秒开 = Rust 直读磁盘 jsonl → React 消息列表(`claude_history.rs` 原生解析,尾部 80 条窗口 + 游标分页 + 800 条 DOM 窗口 + 虚拟列表),进程首次发消息才 `--resume` 惰性 spawn,另有「点开后延迟 1.5s、按会话去重、失败静默」的单点预热。**零批量预付,看一百个会话不起一个进程。**

但它的代价:每个 CLI 一份结构化解析器 + 每引擎一份历史 loader + 消息级渲染层,新 CLI 接入 = 新适配。**tmd-cli 的 PTY 幕布哲学正是为了消灭这个适配矩阵**:任何 CLI(claude/omp/pi/qoder/grok/未来的新面孔)接上 PTY 就是一等公民,字节原样透传,零私有格式知识。走法 1 保住这个优势:磁盘日志就是 PTY 原始字节,回放它同样零适配。

| 维度 | codemoss | tmd-cli 走法 1 |
|---|---|---|
| 秒开原理 | Rust 解析 jsonl → 消息列表 | Rust 读日志尾 → xterm 回放 |
| 每 CLI 适配 | 解析器 + loader + 消息渲染层 | **零**(字节通吃) |
| 历史形态 | 干净消息气泡(可搜索可复制) | 真实 TUI 最终帧 + 滚回(保真) |
| 进程时机 | 首发消息惰性 spawn | 点开后台异步 spawn |
| 新 CLI 接入成本 | 高(三件套) | **零** |

## 走法 1 深入设计

### 语义:点击磁盘会话后发生什么

```
点击磁盘行
  ├─ 同步:创建 tab + 挂载 xterm(零等待)
  ├─ ~100–300ms:sessionHistoryPage 读磁盘日志尾部 → 分块回放进 xterm
  │             (复用 847b4e3 分块 + 96de3cc 进度遮罩,画面即「墓碑帧+滚回」)
  ├─ 后台异步:spawn resume 进程(不挡 UI)
  └─ 进程首字节到达 → 实时流接管(就绪锁语义已有:
     回放未竟时实时字节攒队列,回放尽后按序补写 —— terminalReplay 的保序机制
     本来就是为「回放 + 实时流」排序设计的,直接复用)
```

### 问题一:回放的历史会影响正常继续对话吗?

**不会。** 对话状态与显示状态是两条完全独立的链:

1. **对话状态在 CLI 自己的磁盘会话文件里**(claude 的 jsonl、omp 的 sessions 目录),tmd-cli 的 `~/.tmd-cli/session/**/*.log` 只是 PTY 字节的显示层副本。回放只写 xterm,与 CLI 进程之间没有任何字节交互;CLI `--resume` 从自己的状态文件恢复对话,根本不知道、也不需要知道幕布上放了什么。
2. **视觉衔接由终端语义天然完成**:TUI 类 CLI resume 后几乎必然 `smcup` + 全屏重绘(claude/omp 均如此),新帧直接盖在回放帧上;用户看到的是「旧最终帧 → 活进程重绘」一次无缝切换。万一某 CLI resume 不重绘(追加式输出),最坏情况是回放帧上方接着新输出——可接受,桩目检阶段逐引擎验证。
3. **输入闸**:进程就绪前键盘输入丢弃(现有「回放窗口丢弃历史查询应答」闸语义的直接扩展;查询应答字节同样丢弃——回放里的 DA/CPR 序列不应得到响应)。

需要处理的边界(实施清单):

| 边界 | 处置 |
|---|---|
| 日志终点停在 alternate screen(进程被杀时没来得及 rmcup) | 回放结束即停在该帧;新 CLI 启动自会 smcup/rmcup 重绘接管,无需干预 |
| 回放时幕布尺寸与当初录制尺寸不同 | 最终帧可能轻微错位(光标绝对寻址按旧尺寸),CLI 重绘后自愈;纯 cosmetic |
| 磁盘尾部含 Ask 面板标记(进程死时正挂起) | **是特性不是 bug**:回放字节照常过 askWatch 字节通道,等待标签顺带恢复——与 `ebdccc1` bootAskRestore 的 restoreTail 语义同源,进程就绪后由实时流确认/撤销 |
| 磁盘回放 + 实时流的排序 | terminalReplay 保序机制复用:回放未竟时实时字节攒队列(进程首字节到达时回放通常已竟,竞态窗极小) |
| 回放量 | 从尾部读固定窗口(初定 512KB,实证调)覆盖「最终帧 + 一屏滚回」;更早历史沿用现有「上翻加载磁盘页」管线,零新机制 |

### 问题二:CLI 进程怎么设计(生命周期)

原则:**进程数 = 用户实际点开的会话数**,零预付、有界、可预期。

| 时机 | 行为 | 理由 |
|---|---|---|
| 点击磁盘会话 | 后台异步 spawn resume(不挡点击路径) | 从「点开」到「发消息」的人类反应时间(秒级)天然盖住 spawn 冷启(1–3s),绝大多数情况首条消息零等待——codemoss 的 1.5s 延迟预热都不用抄 |
| 进程就绪 | 首字节到达 → 实时流接管,就绪锁解除,tab 状态标签转活 | 现有 adoptSpawned/首写闸/就绪锁全套不动 |
| spawn 失败 | `sessionStartFailed` 广播 + StartFailureToast(已有);幕布停留在磁盘回放帧,用户可重试 | 失败语义现状 |
| 关 tab | **不杀会话(现状保留)**——后台任务(长编译/hook/dreamer)继续跑,未读灯/Ask 标签继续工作 | `sessionTabs.ts:136` 既定语义,不改 |
| 会话退出 | `removeSession` → `sessionKill` + 清缓冲(现状) | 不变 |
| 应用退出 | `PtyRegistry::kill_all` 清场(`d1f704f` 已落地) | 不变 |
| 内存上的回收 | 想省到底可加「tab 关闭且会话静默 N 分钟 → 杀进程回磁盘态」,**不建议首版做**——现状语义已够用,YAGNI | — |

### 与既有特性的关系

- **自动激活(1e7253d)**:存在理由被走法 1 拆除——「点击等待的大头 = spawn + 回放」拆成「回放从磁盘来(百毫秒)+ spawn 挪后台(不挡点击)」。处置:**整体下掉**(大仙 2026-09-09 拍板),定性与复盘见下节;顺序 = 先落地走法 1 验证,再拆。
- **tab 保活(5bf8e5b)**:不动。磁盘回放只发生在「冷挂载无内存缓冲」的首次点开;保活 tab 切换零回放不变。
- **bootAskRestore(ebdccc1)**:与磁盘回放同源(都读日志尾),实施时统一入口——回放即恢复,避免两条恢复链。

### 自动激活的定性与复盘(2026-09-09 大仙拍板:整体下掉)

- **定性**:痛点真实(点开磁盘会话等 spawn + 回放数秒),解法错配(常驻预付真实进程买点击零等待,代价结构性,调上限只止痛不治病)。
- **spec 复盘**:`2026-09-08-auto-activate-recent-sessions-design.md` 的方案取舍比较了 A 预开 / B 元数据预热 / C 恢复上次活会话,**漏掉了当时已具备条件的磁盘日志先行回放**——`sessionHistoryPage` 翻页原语早已存在,磁盘日志本身就是回放源,不需要进程。设计视野 miss,非执行错误。
- **处置**:走法 1 落地并桩目检 + 实测验证秒开后,整体移除自动激活(设置行为页三输入、`kernel/autoActivate.ts`、boot 钩子、settings 字段;存量设置文件中的 `autoActivateSessions` 键由 sanitize 忽略丢弃,无需迁移)。**顺序不可反**:先建后拆,避免痛点裸奔。
- **保留的副产品**:①`d1f704f` 退出 `kill_all` 清场(正交);②`openDiskSession` 的 `activate/silent` 参数与后台 spawn 链路(走法 1 的后台异步拉起直接复用)。
- **不误伤**:tab 保活挂载(5bf8e5b)解决的是切 tab 重放 + 遮罩的真问题,保留;实测成本可接受(WebContent 330MB,原拟的辅线降耗项已废弃,见辅线节)。

### 工作量估算

- 核心改动:`host.openDiskSession` 点击路径重排(回放先行、spawn 后台)+ TerminalView 挂载源增加「磁盘日志尾」分支(现有「内存缓冲回放」分支的平级兄弟)+ 输入闸扩展到进程就绪前。预估 3 个文件、~200 行净增,无 Rust 改动(sessionHistoryPage 原语现成)。
- 实施前必须核实的两个事实(写 spec 时验证):①磁盘会话 → 最新日志代的映射是否现成(日志按 spawn 代分文件还是续写);②磁盘回放触发 askWatch 的候选升级路径是否与 restoreTail 完全同构。

### 秒开的覆盖边界(默认支持,但要说清的三种例外)

| 场景 | 行为 |
|---|---|
| 有日志的磁盘会话(绝大多数) | **默认秒开**:~100–300ms 出画面,零设置、零配额、零预付 |
| 无日志的磁盘会话(日志被 64MB 旋转截没/从未经 tmd-cli 开过) | 回落现状路径:等 spawn + CLI resume 自绘(1–3s),与今天点开预付外会话的体验相同,无回归 |
| 全新会话(第一次开) | 无历史可回放,走正常 spawn——CLI 自绘启动画面本来就快,不属于秒开诉求场景 |

输入闸口径(统一):**进程就绪前,幕布键盘输入与 Composer 发送一律丢弃,与现有回放窗闸语义完全一致**;极端快手在点开后 <2s 内敲的字会丢,这是现状回放窗的同款行为,不新增排队机制(YAGNI,实测若真有人撞上再加)。

### 辅线(隐藏 tab 停解析 / askProbe 降频 / 滚回降配)

**已整体废弃**(2026-09-09 二轮拍板):主线落地后 WebContent 实测 330MB,远低于原预估区间;停解析与降频各有行为代价(切换补写 ~100ms / Ask 屏幕通道变弱),滚回降配是十分钟常量修改——均不值得养 backlog。若将来内存回潮,从 vmmap 实测数据重新立项,不沿旧账。

### 不建议做

- 砍保活挂载:切换零等待是 0.1.3 卖点,实测 WebContent 330MB 无需再压。
- 动 Rust 泵/日志:实测有界,无收益。
- transcript 结构化视图(走法 2):每 CLI 适配矩阵,弃坑 codemoss 的原因,不回溯。
- 继续调自动激活参数当「优化」:给预付额度讨价还价,不解耦架构。

## 优化后的预期表现

| 场景 | 现状(0.1.3) | 走法 1 落地后(自动激活默认关) |
|---|---|---|
| 冷启 10 分钟整树 | ~5.5GB(16 CLI 预付) | **~0.8GB**(零预付) |
| 3h 长运行整树 | ~6.7GB,监控口径峰值 11.86GB | **~2–3GB**(只有真正点开的会话有进程) |
